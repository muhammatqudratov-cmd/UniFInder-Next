Context: follow-up to the previous admin redesign prompt (already applied — confirmed by screenshot: dark sidebar, pill tabs, colored avatars/badges, FLAGS column are all in place). This second pass closes the remaining visual gaps against the reference design: page header + subtitle + "Add member" button, the three stat cards (Total Members / Active / Flagged), the tab-track + search bar laid out in one row, reordered table columns (MEMBER / MB ID / PHONE / TYPE / FLAGS / STATE) with the full name folded under the nickname, an outlined "USER" badge, a status dot on STATE badges, a warning icon on the FLAGS text, and a simplified pagination row. Still presentation-only except for one explicitly-scoped, fully-grounded addition described below (the 3 stat numbers) — no existing query, mutation, route, or handler is removed or altered in behavior.

Two deliberate, explained deviations from the reference image (kept on purpose, not oversights):
1. The sidebar logo stays the project's real logo (`/img/logo/logoText.svg`) instead of the reference's generic "Membership Console" placeholder text/icon — that name isn't this app's actual brand, and the previous prompt already gave it a clean white chip background that fits the dark sidebar.
2. The member-type filter `<Select>` (All/User/Agent/Admin) is kept, just placed next to the search box — the reference image doesn't show it, but removing it would delete a working filter (`searchTypeHandler`) with no other way to reach it.

Stat cards data — grounded, no invented backend: "Total Members" and "Active" are each one extra lightweight call to the SAME already-existing `GET_ALL_MEMBERS_BY_ADMIN` query (just with `limit: 1` and a different `search` filter) — no new query, no backend file touched. "Flagged" is computed client-side by fetching the same query with a generous `limit` and counting how many of the returned members have `memberWarnings + memberBlocks > 0` — again, the same existing query, just called a third time with different variables. If the real member count ever exceeds the chosen limit, "Flagged" would undercount — call this out to the user as a known limit of this approach (no aggregate "flagged count" field exists in the schema to query directly).

```tsx
										</TableCell>
```

```tsx
											</Button>

											<Menu
												className={'menu-modal'}
												MenuListProps={{
													'aria-labelledby': 'fade-button',
												}}
												anchorEl={anchorEl[member._id]}
												open={Boolean(anchorEl[member._id])}
												onClose={menuIconCloseHandler}
												TransitionComponent={Fade}
												sx={{ p: 1 }}
											>
												{Object.values(MemberStatus)
													.filter((ele: string) => ele !== member?.memberStatus)
													.map((status: string) => (
														<MenuItem
															onClick={() => updateMemberHandler({ _id: member._id, memberStatus: status })}
															key={status}
														>
															<Typography variant={'subtitle1'} component={'span'}>
																{status}
															</Typography>
														</MenuItem>
													))}
											</Menu>
										</TableCell>
									</TableRow>
								);
```
